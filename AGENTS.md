# AGENTS.md

Content-addressable blob store (CIDv1, base32hex) with `dir`, `sql` (SQLite), `http` and `s3` backends. Single Go module, no CI. Storage backends are tested (`storage/storage_test.go`, plain `go test` — table-driven round-trip + a `-race` concurrent-read guard, run against in-memory `httptest` servers for the `http` and `s3` backends); two opt-in *smoke* tests (`TestHTTPSmoke`, `TestS3Smoke`) hit a real server and skip unless their env vars are set. `main` has no tests by convention.

## Build & Commands

```bash
go build -o blob
golangci-lint run          # govet + gocyclo; gofmt/goimports formatters
go test ./...              # run the storage tests (add -race for the concurrency guard)
```

- `blob add <file>` — store file (prints CID). Records `basename(file) → multihash` in the name index
- `blob add --only-hash/-n <file>` — like `ipfs add --only-hash`: print `added <cid> <file>` (one space), do not store
- `blob hash <file>` — print `sha256sum`-style `<cid>  <file>` (two spaces) without storing (equivalent to what `ipfs add --only-hash` gives after the `added` prefix is stripped)
- `blob get <cid|name> -o <out>` — retrieve; argument is parsed as a CID first, falling back to the name index (so `get` round-trips a name passed to `add`); `-o` defaults to using the argument as filename
- `blob lookup <name>` — convenience: name → the stored blob's CID (peek first byte for the codec, then compose + render; not required, the CID is recomputable from the store). Same `Peek`-based derivation the `/name` gateway uses
- `blob serve [--listen/-l <host:port>]` — start a read-only HTTP gateway; default `127.0.0.1:8080`. Serves `GET /blob/<CID>` → the blob, so a stable `blob://<CID>` scheme maps to `http://<host>/blob/<CID>` without the client knowing the backend. Serves `GET /name/<name>` additionally, which `Peek`s the first byte to derive the CID and `302`-redirects to the canonical `/blob/<CID>` (302 not 301, since last-add-wins makes the mapping mutable); read-only: only `Get`/`Peek` are used, there is no upload/`add` endpoint. No `ipfs add -w` directory wrapper is needed for name serving — the name index (per-name, not a second CID) already links name → blob
- Global flags: `--storage`/`-s dir|sql|http|s3` (default `dir`), `--path`/`-p` (default `./.blob-store`); for the `http` backend `--path` is the base URL of the server (e.g. `http://localhost:8080`) and the store lives on the remote side; for the `s3` backend `--path` is the S3/RGW endpoint (host:port or an `http(s)://` URL) plus `--bucket`/`-b` (the named store; or `BLOB_BUCKET`) and, for region-aware S3, `--region`/`-r` (or `BLOB_S3_REGION`), left blank to defer to the server. Remote backends additionally take `--user`/`-u` + `--pass` (or `BLOB_USER`/`BLOB_PASS`; http also `user:pass@` in `--path` or `~/.netrc`) — Basic-auth for `http`, access/secret key for `s3`
- Env defaults: `BLOB_STORAGE_TYPE` (type), `BLOB_STORAGE_PATH` (path), and for s3 `BLOB_BUCKET` / `BLOB_S3_REGION` are used as the flag defaults when the flag is not explicitly set; the flag always wins; `BLOB_USER`/`BLOB_PASS` feed the remote-backend credentials

## Non-Obvious Details

- CID codec depends on content, not extension: file stored with `Json` codec only if first byte is `{` or `[` (`detectCodec` in main.go); anything else is `Raw` (why: DESIGN.md)
- The storage key is the **multihash** (algorithm + digest bytes), opaque `[]byte` (`storage.Digest`). The storage package has no multiformats dependency — it never decodes the multihash, so adding a different hash algorithm (or a different codec) is a `main.go` change only, never a storage change. `computeHash(path) → multihash.Multihash` produces the bytes; `detectCodec(path) → multicodec.Code` picks the content-based codec (Json if first byte is `{`/`[`, else Raw); `computeCID(mh, mc) → cid.Cid` builds the CID (version + codec + multihash — a CID carries no base, that is a render-time parameter); `stringFromCID(c) → base32hex string` is the single point where this store's presentation base is chosen (`StringOfBase(multibase.Base32hex)`) — our choice: the `0-9a-f` alphabet of `base32hex` instead of the `yzabcde…` alphabet of `base32` (go-cid's `String()` default for v1, the one IPFS uses); the key stored is `c.Hash()` (the multihash itself), and `digestFromCID` inverts that at `get` time.
- Dir backend key is the hex of the multihash bytes (not the base32hex CID), fanned out across up to 3 one-byte levels (`fanoutDepth`), the rest as filename: `.blob-store/<b0>/<b1>/<b2>/<rest>` (e.g. `12/20/<byte3>/<rest>` for a sha2-256 multihash), written via tmp-file + rename. The fanout carves the opaque key bytes into 1-byte dir levels — encoding-agnostic, ≤256 per level, no knowledge of the hash algorithm
- SQL backend auto-creates the parent dir of `--path` and the `blobs (hash BLOB PRIMARY KEY, data BLOB)` table (storage/sql.go); no migration steps to run
- HTTP backend (`storage/http.go`) is a thin proxy over plain GET/PUT — no multiformats, no local files. On-wire contract (its own, independent of the user-facing `serve` CID gateway): blobs at `<base>/<hex>` (PUT body=blob, GET streams it, HEAD for existence → `Has`), name index at `<base>/index/<name>` (PUT body = the hex multihash, the same name→hash *link* as the dir symlink / sql foreign key, expressed as file content rather than a symlink; last-add-wins via PUT-overwrite). The hex encoding is chosen only to keep the wire simple and align with the dir backend; the server stores however it likes (no fanout here). `--path` is the base URL. The `dir` backend's fanout and symlink are its *realization* of the same store/index concepts; http has neither (flat path, content-as-link), so the two are similar in concept, not in layout. `Close()` drops idle keep-alive connections (the pool analogue of sql closing its pool). A shared `*http.Client`/`Transport` makes one HTTPStorage safe for concurrent use, so the shared read-only gateway can hand it to every request goroutine like the pooled sql backend
- S3 backend (`storage/s3.go`) speaks the S3 object API via `github.com/minio/minio-go/v7` (primary target Ceph RADOS Gateway; MinIO and AWS also work). Like http it is a thin remote proxy — no multiformats, no local files — and the multihash stays opaque: rendered to hex only to form object keys (blob `<bucket>/<hex>`, index `<bucket>/index/<name>` with body = the hex hash), so it mirrors the http on-wire contract with one level of indirection (the bucket). `--path` is the endpoint (`host:port` → http, `https://...` → TLS), `--bucket` the named store, `--user`/`--pass` the access/secret key (SigV4), and `--region` the SigV4 region (blank = minio-go defers to the server's bucket location). `Get` streams via `GetObject` (an `io.ReadCloser`) and reads the size with a follow-up `Stat` (surfacing the 404 there, since `GetObject` defers the request to the first read); `Peek` is a ranged `GET` (bytes=0..n-1). Not-found is detected from `minio.ToErrorResponse(err).Code == NoSuchKey` (a bare 404 with no S3 XML already maps there, which is why the test shim can return a plain 404). `Close()` is a no-op (minio-go owns its own client/transport); a single `*S3Storage` is safe for concurrent use since minio-go internally serializes/token-buckets, so the shared gateway can hand it to every request goroutine
- Name index is separate from the CAS and stores the blob **key** (the multihash bytes — `storage.Digest` = `[]byte`), *not* a CID string, so each backend resolves a name to a blob with nothing but its own data: dir backend uses `.blob-store/index/<name>` symlinks pointing `../<b0>/<b1>/<b2>/<rest>` (i.e. `../` + relPath) at the blob (written as symlink + rename on a `.tmp` name), sql backend uses a `names (name TEXT PRIMARY KEY, hash BLOB NOT NULL REFERENCES blobs(hash))` table (foreign key, `PRAGMA foreign_keys = ON` on each connection), http backend stores the hex multihash as the body of a single object at `<base>/index/<name>` (a PUT-overwrite — last add wins), and the s3 backend does the same at `<bucket>/index/<name>`. Key is the file basename (expected to be a human-readable name like `ubuntu.sif`, not a CID, so `get`'s CID-first lookup is unambiguous); two names can map to one key and **last add wins** (`Index` overwrites), so `latest`-style aliases stay current. `runAdd` indexes after confirming the blob is stored (so a `Put` failure leaves no dangling name), and still indexes when the blob already exists. The multihash is the key only — the CID (codec + multibase) is derived and is not stored; the dir index symlink follows to content directly, while sql needs a join on `hash` (the FK exists for integrity). Symlinks are Linux-only here; Windows fallback (git's `core.symlinks`-style text target in the file) is the intended migration if ever needed. Per-name files (one row in sql) instead of a shared `index.json` (as OCI registries use): each update is an atomic single-key write (tmp + rename / primary-key upsert), no read-modify-write of one JSON document. This is fine for this store's scale; IPFS avoids any index at this layer since it is content-addressed and distributed, and only gains name resolution via IPNS/DNSLINK — a much larger mechanism (signatures, keys, global lookup) that local `add`/`get` round-tripping does not need
- `StorageBackend` exposes `Close()`: the `sql` backend closes its connection pool (interrupting in-flight reads), the `http` backend's `Close()` drops the client's idle keep-alive connections (in-flight transfers are owned by their request/response), the `dir` backend's `Close()` is a no-op, and the `s3` backend's `Close()` is a no-op too (minio-go owns its client/transport). `main.go` calls `defer backend.Close()` right after constructing the backend in `runAdd`, `runGet`, `runLookup`, and `runServe`
- The `sqlite` backend streams reads via `db.OpenBlob(..., write=false)` (returned as the `io.ReadCloser` from `Get`) instead of `ColumnBytes`, so a blob is never materialized in memory. `Get` opens the blob read-only and closes it through `reader.Close()` before the backend's `Close()` runs (declared in that order)
- Backends open in an explicit `Mode` (`storage.ReadOnly` / `storage.ReadWrite`): `add` opens ReadWrite, `get`/`lookup`/`serve` open ReadOnly (a read-only backend refuses `Put`/`Index` with `storage.ErrReadOnly`, and neither creates the store). `runServe` opens **one shared ReadOnly backend** for the server's life (single open + `defer Close` in `runServe`), handed to every request goroutine. This works because the `sql` backend is now a `zombiezen.com/go/sqlite/sqlitex` **`Pool`** (size 10), not one `*sqlite.Conn` (which is a single C handle, not safe concurrently — sharing it SIGSEGV'd, verified): each op takes a conn, does its work, puts it back; `Get`'s reader keeps its conn checked out until `reader.Close()` (`connReader` in sql.go), so streaming blobs across the pool is safe. Read/write overlap is via WAL (`OpenWAL` on ReadWrite opens), so an `add` does not block concurrent readers. The `dir` backend needs no locking (one file handle per op, atomic tmp+rename), and the `http` and `s3` backends are both safe to share across goroutines (http via its pooled client's keep-alive connections, s3 via minio-go's internal request serialization) — each `Put`/`Index` writes a distinct key, so there is no cross-key contention to guard.
